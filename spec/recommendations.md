# Recommendations

- Filter by the user's stated constraints first. Rank eligible places by request relevance, then explicit preferences. A listing, cuisine tag, or rank is not evidence of atmosphere, seating, availability, or booking.
- Keep source features grounded and timestamped. Use provider categories where they exist; leave unsupported traits unknown. Do not extract features with an LLM on every view or interaction. If free-text evidence later needs interpretation, process it when the source changes and reuse the result until it expires.
- An explicit preference affects the open chat immediately. Count only distinct actions that actually express taste, such as “more like this” or a direct rejection; a view or place selection alone is not an endorsement. Keep one-off feedback in the session unless the user asks to remember it. Let repeated, independent signals justify a durable inferred preference; choose that evidence threshold from observed behavior, not a fixed timer. Use deterministic updates before considering a model call.
- Resolve conflicts in this order: current request and hard constraints, explicit choices in this chat, remembered preferences, then inferred patterns. A preference may break ties among eligible places; it must not override a conflicting request or turn weak evidence into a fact about a venue. Keep the context of a signal—such as a group dinner versus a solo lunch—before treating it as a general taste.
- A search for another person is not evidence of the account holder's taste. A choice for one occasion need not generalize to another; keep its scope until the user asks to remember it or independent evidence supports a broader preference.
- Treat skipped cards as weak evidence and a direct “do not show this place” as a strong, venue-specific instruction. When sources disagree about a venue, preserve their provenance and freshness; do not silently promote one category or old menu into a current fact.
- With little or no preference history, rank from the current request and grounded place facts. Do not require personalization to make a useful recommendation.
- Cuisine ranking slice: read saved onboarding cuisines once per chat turn, combine them with the explicit “More cuisine” choice for that chat, and pass this bounded cuisine context to the agent and place ranker. An explicit venue or cuisine request sets ranking order for that search. Map selections may persist as thread navigation context, but never become taste signals. Explicit dish selections are separate bounded evidence of interest for model context, not inferred cuisine or place-ranking scores.
- Keep the recommendation handoff inspectable: requested constraints, eligible place facts with provenance, short-lived session choices, and durable preferences remain distinct. Retain only the user data needed to update preferences; do not store a browsing history by default.
- Give the agent provider-neutral capability names, evidence, and limits. Keep vendor names in internal provenance, traces, and adapter code rather than tool descriptions or conversational filler. Name a booking destination when the user must decide whether to leave the app. Display required map and data credits in the map surface, separate from the assistant's answer.
- Chat transcripts and explicit UI selections belong to a saved, account-owned thread. Session cuisine choices survive reopening that thread, but do not become account-wide taste automatically. Account preferences live in the passport, sharing onboarding's controls and validation; saving preferences does not reset chat history.
- Passport presents taste controls and the visit ledger as adjacent sections when space permits, stacking on compact screens. Use alignment and spacing rather than separator rules to establish hierarchy; keep selections visually distinct and save explicit. Chat selections sit with the composer as removable context, separate from transcript prose.

- The empty home chat shows one warm invitation above the scene carousel, using the account's first name and up to two saved cuisines, or a saved outing when cuisines are absent. With no preferences, use a general invitation. Reuse the loaded profile; make no extra model/provider call, invent no venue or availability, and hide the invitation when the transcript begins. Allow the sentence to wrap on compact screens.

- Atmosphere preferences use labeled, static gradient tiles in a horizontal carousel, with visible selection and keyboard access. Color represents user taste, never verified venue atmosphere. Cuisine choices are searchable suggestions, not a closed taxonomy: allow bounded custom names, show removable selections, and save explicitly.

- The home scene carousel shows the top five scene types: saved outing matches first, then unmatched scenes in the existing fallback order. Saved matches retain their existing scene order; there are no inferred taste weights yet. These are starting prompts, not venue recommendations or additional taste signals.

- Adding a passport memory is an open visual composition, not a disclosure or boxed administrative form. A live stamp preview reflects the chosen outing; place, date, and outing are directly editable. Keep save explicit and distinguish unsaved input from saved memories. Saved records stay behind a circular count below Save memory; opening it reveals a bounded collection without expanding the page.

- Menu cards show source-grounded dishes with restaurant, area, and source URL; unsupported names, ingredients, prices, and availability remain unknown. Explicit selections use `selectedDishes: DishSelection[]` with `{ id, name, restaurant, area, sourceUrl, selectedAt }`, persisted in the existing account-owned `chatThread.context` on the next submitted turn. A card view is not a taste signal.
- Load explicit dish interests from the 20 most recently updated account-owned threads, bounded to 12 distinct restaurant/name pairs with current chat selections first. Keep this separate in model context from saved declared cuisines; the current request takes precedence. This is bounded evidence of interest, not unlimited learning, consumed food or visit proof, an allergy/ingredient/cuisine inference, a hard constraint, or automatic proactive state. Do not add dish scoring to `rankPlaces` when candidates lack grounded menu evidence. Reuse thread storage without a new table, migration, or model call.
