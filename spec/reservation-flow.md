# Reservation flow

- Find and show all verified times for the requested date, party size, and window. Distinguish live availability from candidate places and incomplete searches.
- Carry cuisine into reservation-page discovery. Area-only results are leads; choose a suitable named venue before browser inspection, trying explicitly accepted alternative cuisines in the same area before widening the location. Reuse unchanged discovery while collecting missing booking details. An ordering-only or unverifiable candidate does not finish an area-and-cuisine reservation request: continue with another matching booking destination or venue within those constraints before asking to expand them. Preserve explicit named-venue requests.
- When a time window is given, keep exact matches distinct from verified times up to 30 minutes nearby. Retry a retryable browser inspection failure once; a booking link alone never establishes availability.
- Browser inspection follows the conversation's venue, area, and prior reservation link across public booking destinations. Constrain a provider only when the user requests it. Retain both place listings and booking-page references across turns; an area lookup failure must not prevent inspecting an independently found booking page. Verify the displayed venue, selected date, and guests before exposing times, and recheck the selected time before checkout.
- Keep place identity across turns. Expire time-sensitive observations by their check time: reservation times after 60 seconds and current weather after 10 minutes; recheck before checkout or a new claim of current availability. Expired facts stay in the visible transcript as history, not as selectable times or live evidence.
- Chat sends only the newest user message and current selections; the server loads and compresses stored history as described in [chat-persistence.md](chat-persistence.md). An oversized newest-message request cannot be reduced by dropping browser history: show the rejection, preserve the visible transcript, and offer a new chat without automatically repeating it.
- Search by venue, neighborhood, or named public origin. Show origin and destination pins; use travel time for “nearby.” Explore neighborhoods as areas with sourced context, not unsupported scores.
- Keep one rolling place map per resolved area, anchored where that area first appeared. Repeated searches replace its pins and cards with the latest completed result; separate areas retain separate maps. Empty results clear the previous map. Keep original tool evidence in chat context, and keep the footer reply hint short rather than repeating the follow-up question.
- Rank eligible place listings by the requested venue and sourced cuisine category, then use explicit preferences as a tie-break. Apply the evidence and feedback rules in [recommendations.md](recommendations.md).
- Fit includes ambiance and the requested room, section, or table. Claim a seat is selectable only when the provider offers it. If a call is needed or online details cannot be verified, show a verified reservation number and what to ask.
- Map cards show sourced cuisine and address when available. A cuisine-match label requires agreement with the current search; popularity and atmosphere labels require their own evidence. Card selection activates its numbered pin and moves the map; pin selection reveals the corresponding card.
- Concierge helps put a plan together with a warm, conversational voice: acknowledge the user's preferences naturally, start discovery before collecting all booking criteria, and offer a grounded next step. Ask only for details that block the next useful action; clear guest-count replies need no reconfirmation. Fresh checked times can be called available. Inspection failures do not imply no tables or an unsupported party size. Routine caveats stay out of availability replies; freshness checks, checkout terms, and final confirmation remain required.
- The agent calls `followup` through `execute` to ask a blocking question and end its turn. The question is its own assistant bubble; reply controls and any calendar sit beside it as separate surfaces in the same turn. The footer owns free-text replies; inline controls show natural answer labels for categorical questions, such as “1 person” or “2 people” for guest counts, without letter prefixes. The follow-up declares the missing answer type (text, partySize, date, or time), and the runtime accepts a calendar only for date/time questions. Ask one missing detail at a time, preserving already supplied values. The agent chooses month, day, or time according to the unresolved detail: missing month, missing day within a known month, or missing time on a known date. Follow-ups show only that picker: a twelve-month grid with year navigation, a day grid within the chosen month, or a prominent native time field with the known date as quiet context. No view tabs or redundant date input on a time question; committing a day submits one date reply. Keep the known date and local HH:mm time as presets. A month reply YYYY-MM opens the day picker through followup; accept it as a calendar preset only for month/day views, anchored to its first day for display. It does not select a booking day and must not be passed into reservation checks. An unresolved month must not be silently inferred from a day number. Reservation results show only the model-selected view, without view tabs. A date/time follow-up takes priority over an inspection in the same turn; preferred-time replies request another availability check and do not select a table. Older inspections show a plain historical summary instead of disabled controls. Reservation results can use the same views for verified times and personal conflicts. Committed clarification choices trigger one reply and remain context; browsing alone does not submit. Choosing a verified reservation slot updates local selection immediately without a model turn; Continue to checkout sends that selection and rechecks it before provider advancement.
- Browser previews show JPEG frames captured by the existing inspection connection after navigation and each inspection step. Frames are transient chat events, not model context or persisted transcript; accept only bounded JPEG data URLs for an active session. Closing inspection removes the preview. The optional external view binds its expiring account-bound ticket to the exact inspected page.
- Assistant text stays on the assistant's side regardless of tool output; answer controls remain right-aligned. A browser preview opens explicitly and offers an account-bound external view.
- Authorized calendar access may mark conflicts without exposing event details or creating events.
- Before handoff, show venue, date, local time, party size, and terms. Stop before final booking submission or payment; never claim a booking without confirmation.
- Browser E2E evidence distinguishes mocked UI regressions from opt-in real chat/provider journeys. Preserve each run locally with committed replies, streamed tool evidence, failed UI step, and real Sentry trace IDs. Unexpected test failures may report bounded summaries to Sentry in the e2e environment; authenticated browser artifacts stay local. Frozen Braintrust scoring uses the same run ID and separates browser completion, transport, and model argument failures. A test must not submit a booking.

- The home and passport header places Google Calendar beside the avatar: an icon-only white squircle with a black Google logo, accessible Connect action before consent, and a green check when stored Calendar scopes are present. A muted calendar tile may sit behind Google as a decorative stack; it does not indicate Apple Calendar consent or offer unsupported Apple/Gmail connection actions. This indicates authorization, not a successful live calendar read.

- Named restaurant information uses `places.lookup`: bounded Browserbase web search and up to two page reads, independent of geocoding, booking date and guest count. A missing nearby-map listing must not end a named lookup. Keep cited page content, search links and page-read failures distinct; no availability follows from restaurant information. Explicit venue selection overrides an earlier inferred cuisine.

- Restaurant menus use `menus.lookup`, reusing named web lookup and one bounded, source-checked extraction. Render a compact standalone card beside the assistant message, initially four dishes with progressive disclosure. Dish toggles update selected context without sending a message; the next user turn forwards them. Show source and read date; an excerpt is not a complete or current inventory, and selecting food is not ordering it.
